# 性能基准（大书）

> 可复现：`npm run bench:large`（本地生成 1000 章，不联网、不花钱）。
> 测试机：Windows 11 / Node 24 / Electron 45；数字取三次运行的中位数量级。

## 1000 章 / 约 270 万字

| 指标 | 结果 | 说明 |
|---|---|---|
| 章节文件体积 | 8.03 MB | 1000 章正文 |
| 首次建索引 | ~1.8 s | 切块 + 1/2-gram 索引 + 持久化 |
| 索引体积 | 16 MB | `.studio/index/search-index.json` |
| 检索（5 个关键词查询） | ~0.5 s | 索引大后为 ~100 ms/查询（BM25 全库打分） |
| 修改一章后的首次检索 | ~0.29 s | 读全库算 hash + 只重建该章 |
| 上下文包组装 | ~83 ms | 含读取上一章正文与知识文件 |
| 书快照（冷启动，首次读全书） | **197 ms** | 构建 `.studio/cache/chapters.json` 字数缓存 |
| 书快照（热读取，只 stat） | **67 ms** | 缓存命中后不再读章节正文 |
| 索引内存占用 | 约 16–20 MB | 常驻在 Agent utilityProcess |

## CI 性能回归门槛

`npm run check:perf` 用固定语料（200 章 × ~600 字）跑一遍核心路径，阈值故意比实测宽很多，
只拦「灾难性退化」（例如某次改动把快照重新变成全量读盘）：

| 指标 | 本机实测 | CI 门槛 |
|---|---|---|
| 快照（冷启动） | ~22 ms | 5 s |
| 快照（热读取） | ~5 ms | 1.2 s |
| 上下文包组装 | ~3 ms | 1.2 s |
| 索引构建 | ~85 ms | 45 s |
| 4 次检索 | ~15 ms | 4 s |

CI 只在 Ubuntu verify job 跑（Windows 已有 E2E），避免拖慢整体流水线；阈值可用
`PERF_MAX_*` 环境变量临时调整。

## 设计取舍

- **检索前不做全库重读**：首次构建后监听 `chapters/` 目录（`fs.watch`），
  文件变化后标记 dirty，下一次检索才做 hash 对齐；
- watcher 不可用时退化为每次全量校验（正确性优先，慢一些）；
- 索引只存 chunk + preview，不存整本书的重复副本以外的数据；
- 上下文包按模型预算裁剪，与书的总字数解耦（大书不会把 prompt 撑爆）。

## 对比：更早的小语料基准

300 章 / 80 万字时：索引 ~1.2 MB、查询 ~4 ms、改一章增量 ~4 ms。
索引与查询成本随章节数近似线性增长，1000 章仍在"点一下即出结果"的量级。

## 已知瓶颈与后续

- BM25 全库打分在 **3000+ 章** 时会开始变慢，可考虑按卷/章节范围过滤或分层索引；
- `listChapters` 的字数统计已做缓存（size + mtime 失效），热快照从 197ms 降到 67ms；
  上下文包组装 ~30–80ms（随上一章大小波动），后续可进一步缓存摘要；
- 大书首次打开时建索引 1–2 秒，已有进度提示（检索工具调用时构建）。
